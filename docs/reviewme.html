ReviewMe

A bot that reviews your Pull Requests and posts real inline comments, line by line.

Key points Several specialized reviewers analyze a PR in parallel — technical, ticket coverage, translations. Each has its own inputs and output format. The engine validates every remark against the diff, deduplicates, caps, and posts in a single write.

How it works

The project enables the reviewers it wants; the diff triggers the ones it concerns. A reviewer unrelated to the PR does not run — that is the main cost lever.

What it can do

CapabilityBehavior
CommentsInline line-by-line anchored on the lines actually changed, plus a summary
Re-reviewContent-anchored dedup: a commit that shifts lines creates no duplicate
ThreadsReplies in the existing thread when the code of a commented line changes
ConventionsRead from the reviewed repository (AGENTS.md, docs/), never copied
InputsCLI · webhook · poll · CI (GitHub Actions, Bitrise)
IdentityPAT, or a dedicated GitHub App (<slug>[bot]) with a renewed token
Looking for a setting? Recipes lists common needs and the line to write — triggering, noise, cost, context, deployment.
Ballpark A review costs $0.3 to $2.4 and takes 1 to 8 minutes depending on diff size — cost follows the size of the diff, not the number of reviewers. Always start with --dry-run: everything is computed and displayed, nothing is posted.

Understand

Reviewers

Several specialized reviewers on the same PR.

Key points Each reviewer has its own inputs and output format. They run in parallel; the GitHub write stays single.

Why several reviewers

Not to lighten a prompt: because the inputs and outputs differ.

"AC3 not covered" has no line to point to — it is an absence, not a located error. A technical finding does. Two output formats, hence two reviewers.

ReviewerGoalInputsOutputTrigger
techArchitecture, security, performance, reliability, conventionsdiff + repo conventionsinlineevery PR
usAre the acceptance criteria covered?Jira ticket + diffglobalticket key detected
i18nCompleteness and quality of translationslocale files + diffmixedwhen.paths

These are typical goals shipped in config/templates/, not shared prompts: each project starts from the skeleton then writes its own persona.

Two levels of selection

1 · Activation
the project chooses its reviewers
→
2 · Triggering
the diff decides who runs
→
3 · Execution
in parallel, single write

Level 2 is not a nicety: without it, every PR pays for every enabled reviewer. Four systematic reviewers ≈ $3 per PR.

i18n only starts if the diff touches a locale. us, only if a ticket key is detected.

Single write and cap

Reviewers run in parallel — one claude -p each. The GitHub write goes through a single point.

Three reasons: shared dedup, the limit of 80 creations/minute, and the comment cap — impossible to compute reviewer by reviewer.

The real risk Four zealous reviewers = 15 comments = the developer tunes out and disables the bot. MAX_COMMENTS_PER_PR (default 10) cuts per PR, across all reviewers, keeping the most severe then the most certain. The rest is logged, not posted.

Conventions are not copied

A project already documents its rules. Copying them into the config creates a copy that silently drifts.

Nobody notices: the reviewer keeps confidently quoting old rules.

So a reviewer declares what to read, and the engine resolves it at every review:

# reviewer.toml
[context]
read = ["AGENTS.md", "documentations/CODING_STYLE.md", "documentations/"]
DeclaredWhat the engine does
a fileInjects its content — always up to date, and the agent cannot "forget" to read it
a folderInjects the inventory of its .md files; the agent opens what concerns the PR
a missing pathExplicit WARNING in the logs
a path outside the repositoryRejected (../, absolute path)
The gain When a conventions file is renamed or deleted, the WARNING flags it on the next run. Without a declaration, the reviewer would lose its rules without anyone noticing — it would keep commenting, just worse.

So common/ only keeps what exists nowhere in the repo: language, tone, length of remarks, false positives never to produce — shared by all the project's reviewers.

Deterministic before the LLM

A reviewer can declare a precheck: a script whose output is injected as established facts.

"The key checkout.title is missing in de" is verifiable — free, instant, no false positive. The model keeps the judgment: unsubstituted variables, plurals, length, tone.

Never pay an LLM for what a diff does better.

Learning from feedback, without absorbing it

The bot remembers nothing from one PR to the next: a point rejected yesterday comes back tomorrow. It does not learn on its own either — a rule absorbed silently would gradually make it blind without anyone knowing why.

The mechanism is attribution: a rule carries its author, its PR and its date, so it stays contestable.

reviewme feedback --pr 16974

- **CartView.swift** — the `tech` reviewer said: "Force-unwrap on a URL from the API…"
  **alice** replied (PR #42, 2026-01-15): "The API guarantees this field by contract."

These lines are proposed, not decided. A human reviews them — a one-off reply is not a rule — then pastes them into common/team-rules.md, which is injected into all the project's reviewers.

Instruction given to the reviewerWhy
Apply these rules, but they are opinions, sometimes contextualThey come from a specific PR, not from the project's docs
When you stay silent because of a rule, quote itWithout the mention, nobody can contest it — and another developer may disagree
If the code clearly contradicts a rule, report it anyway and explainThe situation may have changed, or the author was talking about another case

Since the file is versioned, a rule is discussed in a pull request and undone with a git revert.

No subagents

A reviewer cannot delegate to subagents, and the Task tool is not in the allowlist. This is not an oversight.

Verified A subagent does not inherit its parent's allowlist: it uses the tools of its own definition. A parent restricted to Read,Glob,Grep was able to run whoami through a subagent declaring Bash. Since a reviewer's configuration can come from the reviewed repository — hence from a Pull Request — that would reopen arbitrary code execution.

To vary the model by task, the equivalent already exists and costs less: create one more reviewer with its own model. It is declarative, the count is bounded, each run has its budget, and everything goes through the engine's allowlist.

Plugins

A reviewer may need skills or agents that do not live in ReviewMe — in-house tooling, specialized analysis. It declares them, and the engine installs them before the review:

# reviewer.toml
[plugins]
marketplaces = ["owner/marketplace-repo"]   # added first
install      = ["my-plugin"]                # or "my-plugin@marketplace"

Idempotent: what is installed is not installed twice. A failure only affects the reviewer concerned.

Third-party code Installing a plugin runs code you did not write in the review environment, alongside the job's secrets. A plugin is reviewed like code. The engine keeps its tool allowlist: a plugin skill gets no more rights than the reviewer that invokes it — which also limits what a heavily tooled plugin can do here.

Naming a reviewer

A reviewer's id is the name of its folder. It is free: tech, us and i18n are the skeleton's conventions, not imposed values.

reviewers/mobile-security/     # perfectly valid
reviewers/perf/
reviewers/accessibility/

No code depends on these names. What defines a reviewer is its reviewer.toml and its persona.

Once chosen, leave it alone The id is part of the deduplication marker. Renaming it on a repository already commented on orphans all its comments: they will be reposted as duplicates.

Required contexts

requires declares the external data without which a reviewer makes no sense. If missing, it is skipped — never an error, the others carry on.

ValueWhat it bringsProvided by
jira_ticketTitle, description and acceptance criteria of the ticket linked to the PRJIRA_BASE_URL, JIRA_EMAIL, JIRA_API_TOKEN

The only value to date. An unknown value is rejected at load time: without this check, requires = ["jira"] would make the reviewer permanently inert, without a single message.

Four steps, done once. It is the simplest shape to start on a project.

The risk to cover If the config lives in the reviewed repository, a PR can modify its own review — soften a persona, disable a reviewer. The engine closes the most serious consequences: an instance's .env cannot define what is executed nor where authentication happens (CLAUDE_BIN, tokens, PATH… are ignored), and a precheck cannot leave its reviewer's folder. What remains are changes of judgment: for those, protect .reviewme/ with CODEOWNERS, or load the config from the base branch rather than from the PR.
Safer in CI Materialize the config from the base branch instead of the PR tree: 
CFG=$(mktemp -d)
git fetch --quiet --depth 1 origin develop
git archive FETCH_HEAD .reviewme | tar -x -C "$CFG" --strip-components=1
export REVIEWME_CONFIG_HOME="$CFG"
The PR can then no longer influence its own review, even before merge.

In CI: the instance pins the engine

In CI, no engine changing version between two builds. The instance mounts it as the .core submodule and pins its version: a single clone brings everything.

# in the instance repository, once
git submodule add <engine-url> .core

# in CI
git clone --recurse-submodules <instance-url> config
cd config && ./reviewme review --pr "$PR_NUMBER"

The launcher detects .core on its own, no variable to set. Without a .venv, it goes through uv run.

Updating the engine becomes a dated move: git -C .core pull then commit the pointer.

Direction of the mount It is the instance that pins the engine, never the reverse. The engine references no instance, stays neutral, and can be shared or published — whereas an engine that mounted its instances as submodules would be polluted by a pointer commit at every persona change.
Understand

Under the hood

From the diff to the inline comment, and the modules that handle it.

Key points The engine returns JSON findings; ReviewMe validates each line against the diff (otherwise 422), deduplicates with a stable fingerprint, posts in a single write, and replies in threads when a line has moved.

1 · Structured findings

claude -p, with the reviewer's persona, answers with JSON: summary + findings {path, line, severity, message, snippet, confidence}.

Invalid JSON? Fallback to a global comment rather than a crash. The review is delivered, less nicely, never lost.

2 · Anti-422 validation

GitHub validates a review atomically: a single comment outside the diff rejects the WHOLE review.

diff_utils parses the patches and computes the commentable lines. Findings outside the diff move into the summary.

3 · Fingerprint & deduplication

Each comment carries an invisible marker: <!-- reviewme:REVIEWER:HASH -->, with HASH = sha1(path + line content).

Independent of the line number and of the text narrated by the LLM, hence stable between two runs.

We recognize our comments by this marker, never by the author — otherwise we would touch human threads.

The deduplication key is the pair (reviewer, hash). That is what lets two reviewers comment on the same line without one making the other disappear.

Key property The hash covers the content of the line, not its number: a commit that shifts the code recreates no comment. The reviewer_id is a prefix of the marker and is not part of the hash. Locked by tests/test_fingerprint_migration.py.
Pitfall REVIEWER_ID must remain stable over time for a given project: renaming it orphans all the comments already posted, which will then be reposted as duplicates. Same rule as for the hash.

4 · On a new commit

SituationWhat the bot does
The issue is there, the line has not moveddedup nothing posted, nothing said
The issue is there, the line has movedreply in the existing thread — never a new comment
The issue is gone and the line has changedreply "this point no longer appears — fixed"
The issue is gone but the line is identicalsilence nothing is concluded

The last row is the safeguard: otherwise a model that varies from one run to the next would be enough to announce an imaginary fix. Only something verifiable is concluded — GitHub marked the comment outdated, so the line really changed.

A reviewer only replies in its own threads: the marker carries its identity.

4 · What the agent knows about the PR

At every review, the agent receives its previous remarks and the human replies — not just the diff.

SituationEffect
A point already reportedIt does not repeat it: it is already visible on the PR
"This is intentional"It does not come back to it, even if the line has moved
A fixed pointSilence — no congratulations

Without this history, a "this is intentional" is forgotten as soon as the line's code changes: the fingerprint differs, and the remark comes back. That is what makes a team end up turning the bot off.

Third-party content Replies come from developers: they are injected as data, with the explicit instruction not to follow any instruction in them.

4 · Thread lifecycle

SituationAction
New findingAdded to the inline batch
Finding already posted, still validDedup — nothing
Finding persists, comment became outdated (new commit)Reply in the existing thread (no duplicate)
Invalid engine JSONFallback: global comment
Residual 422 on the batchFallback: everything as a global comment (nothing lost)

The inline batch = a single POST /pulls/{n}/reviews (respects the 80 creations/min limit).

Deploy

Four entry points, three targets, and the safeguards to know.

Key points Everything goes through the same run_review() building block; entry points only resolve a PR and call it. Before exposing anything, read the security section: a PR author is not trustworthy.

Entry points

No duplicated review logic: each entry resolves a PR then calls run_review(). You choose the entry according to the deployment context.

CLI (one-shot)

  • reviewme review --repo --pr
  • The shared building block
  • Ideal for: CI, cron, manual testing

Webhook

  • pull_request event → review
  • HMAC required (fail-closed)
  • Ideal for: real-time VPS

Poll

  • Loop over labeled / all PRs
  • No inbound exposure
  • Legacy / dev mode

CI

  • GitHub Actions or Bitrise
  • Calls the one-shot CLI
  • 1 build = 1 review
Recommendation Start with the one-shot CLI (nothing to expose, validates the whole chain). Move to the webhook for real time once the VPS is properly exposed (TLS + HMAC).

Deployment

Whatever the target, deployment clones the instance (with the engine as the .core submodule) and calls its launcher — see Get started § In CI.

Linux runner, even for an iOS project The review compiles nothing: it reads a diff and text files, without Xcode or a toolchain. Bitrise lets you override the stack per workflow (meta.bitrise.io.stack), so an iOS app can have its review workflow on Linux — much cheaper per minute than a macOS runner. Full example: deploy/bitrise-step.md.

Ready-made recipes in deploy/. The point to settle at deployment remains the engine's auth in a non-interactive session: ANTHROPIC_API_KEY, or an enterprise gateway via ANTHROPIC_BASE_URL.

History on an ephemeral runner

A CI runner starts from scratch at every build: no cumulative statistics, and a rerun on the same commit pays again for a review that will post nothing.

The engine writes two things in data/:

FileContentPortable?
data/stats.jsonCounters only: cost, remarks posted, deduplicated, discarded, per author. No title, no message, no code excerpt.Yes this is what goes in the cache
data/reviews/The details of a review, model summary includedNo content of real PRs
# Bitrise: two steps around the review
- restore-cache@2:
    inputs: [key: reviewme-ios-history]
- script@1: { ... }
- save-cache@1:
    is_always_run: true        # even if the review fails: the counters count
    inputs:
      - key: reviewme-ios-history
      - paths: $HOME/reviewme-data

Statistics are idempotent per (PR, commit): replaying a build does not inflate the totals. The dashboard serves them on /api/stats, including when review details are missing.

A cache is not storage It gets evicted and is scoped by key. For counters, a loss costs a gap in the history. For anything else, plan a real store.

Security

Read before any deployment A PR author is untrusted. Without precautions, the diff can push the engine to write files (RCE) or exfiltrate secrets into a public comment. The safeguards below are implemented; the network sandbox remains to be wired at deployment.

Safeguards in place

ThreatMitigation (implemented)
Arbitrary write (injection → RCE)Locked allowlist Read,Glob,Grep,Bash(git log/show/diff) — no Write, never --dangerously-skip-permissions
Secret exfiltrationDiff treated as untrusted data; scrub (tokens, keys, absolute paths) on all text before posting
Spoofed webhookHMAC X-Hub-Signature-256 in constant time, raw body, fail-closed without a secret
Overpowered tokenFine-grained PAT, 1 repo, PR R/W (no classic repo)
Exposed dashboardCORS * removed, /api/requeue write endpoint removed, read-only on 127.0.0.1
Secret/data leak.gitignore covers .env and data/
Still to do at deployment The #1 mitigation against prompt injection — running claude -p in a sandbox without outbound network (except GitHub) and with Read confined to the target clone — cannot be handled in code: it must be wired at the infra level (container/systemd + firewall). The scrub is the last barrier, not the only one.
Dedicated identity Run the bot under a GitHub App rather than a human PAT: short-lived token renewed automatically, explicit permissions, and comments arrive under <slug>[bot] instead of a person's account. Just fill in GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY_PATH.

Status & limits

What runs, what does not exist yet, and what needs calibrating.

Key points The core is validated on real PRs: inline comments anchored to the right lines, no duplicate after a commit that shifts the code, and several reviewers in parallel on the same diff. Two settings remain to be tuned by hand on each repository: the confidence threshold and the cost cap.

Validated on real PRs

CheckResult
Inline on the right linesOK re-anchoring by content when the model is off by a few lines
Dedup on re-reviewOK same commit and next commit: zero duplicates
Multi-reviewer fan-outOK two reviewers in parallel, a single GitHub write
Triggering by the diffOK a reviewer only runs if the PR concerns it
Conventions read from the repositoryOK and an obsolete path is reported

To calibrate on each repository

SettingWhy
CONFIDENCE_THRESHOLDAt 80, most findings are filtered out on already-reviewed code. Run a few PRs with --dry-run and look at what would have been posted before deciding.
MAX_BUDGET_USDCost follows the size of the diff: a large diff costs more than one more reviewer. The cap applies per reviewer.
MAX_COMMENTS_PER_PRWhat makes teams abandon a review bot is noise, not a lack of findings.

What does not exist

MissingPractical consequence
Deployment sandboxTo be wired at the infra level (no outbound network, confined FS). It is the fundamental mitigation against prompt injection — see Security.
Blocking REQUEST_CHANGESThe bot only posts COMMENTs. Requires a GitHub App as identity.
Resolve / unresolve threadsGitHub already collapses comments that became outdated.
Multi-line comments and suggestionsA finding is anchored on a single line, right side of the diff.
Hard stop at a PR's cost capReviewers run in parallel: the overrun is logged, not interrupted.
