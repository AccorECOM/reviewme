ReviewMe

Un bot qui review vos Pull Requests et poste de vrais commentaires inline, ligne par ligne.

L'essentiel Plusieurs reviewers spécialisés analysent une PR en parallèle — technique, couverture du ticket, traductions. Chacun a ses entrées et son format de sortie. Le moteur valide chaque remarque contre le diff, déduplique, plafonne, et poste en une seule écriture.

Comment ça marche

Le projet active les reviewers qu'il veut ; le diff déclenche ceux qu'il concerne. Un reviewer qui n'a rien à voir avec la PR ne tourne pas — c'est le principal levier de coût.

Démarrer

Le moteur d'un côté, votre configuration de l'autre.

L'essentiel Le moteur est un dépôt ; votre instance (projets, personas, .env) en est un autre. Une variable les relie. En local on garde deux clones, en CI l'instance embarque le moteur en submodule.

Comprendre

Reviewers

Plusieurs relecteurs spécialisés sur une même PR.

L'essentiel Chaque reviewer a ses entrées et son format de sortie. Ils tournent en parallèle ; l'écriture GitHub reste unique.

Pourquoi plusieurs reviewers

Pas pour alléger un prompt : parce que les entrées et les sorties diffèrent.

« AC3 non couvert » n'a aucune ligne à pointer — c'est une absence, pas une erreur située. Un finding technique, si. Deux formats de sortie, donc deux reviewers.

ReviewerObjectifEntréesSortieDéclenchement
techArchi, sécurité, perf, fiabilité, conventionsdiff + conventions du repoinlinetoute PR
usLes critères d'acceptation sont-ils couverts ?ticket Jira + diffglobalclé de ticket détectée
i18nComplétude et qualité des traductionsfichiers de locale + diffmixtewhen.paths

Ce sont des objectifs types livrés dans config/templates/, pas des prompts partagés : chaque projet part du squelette puis écrit sa propre persona.

Deux niveaux de sélection

1 · Activation
le projet choisit ses reviewers
→
2 · Déclenchement
le diff décide qui tourne
→
3 · Exécution
en parallèle, écriture unique

Le niveau 2 n'est pas un confort : sans lui, chaque PR paie tous les reviewers activés. Quatre reviewers systématiques ≈ 3 $ la PR.

i18n ne part que si le diff touche une locale. us, que si une clé de ticket est détectée.

Écriture unique et plafond

Les reviewers tournent en parallèle — un claude -p chacun. L'écriture GitHub passe par un seul point.

Trois raisons : dédup partagée, limite de 80 créations/minute, et plafond de commentaires — incalculable reviewer par reviewer.

Le vrai risque Quatre reviewers zélés = 15 commentaires = le développeur décroche et désactive le bot. MAX_COMMENTS_PER_PR (défaut 10) coupe par PR, tous reviewers confondus, en gardant les plus graves puis les plus sûrs. Le reste est journalisé, pas posté.

Les conventions ne se recopient pas

Un projet documente déjà ses règles. Les copier dans la config crée une copie qui diverge en silence.

Personne ne le voit : le reviewer continue de citer d'anciennes règles avec assurance.

Un reviewer déclare donc ce qu'il faut lire, et le moteur le résout à chaque review :

# reviewer.toml
[context]
read = ["AGENTS.md", "documentations/CODING_STYLE.md", "documentations/"]
DéclaréCe que fait le moteur
un fichierInjecte son contenu — toujours à jour, et l'agent ne peut pas « oublier » d'aller le lire
un dossierInjecte l'inventaire de ses .md ; l'agent ouvre ce qui concerne la PR
un chemin absentWARNING explicite dans les logs
un chemin hors du dépôtRefusé (../, chemin absolu)
Le gain Quand un fichier de conventions est renommé ou supprimé, le WARNING le signale au run suivant. Sans déclaration, le reviewer perdrait ses règles sans que personne ne s'en aperçoive — il continuerait de commenter, simplement moins bien.

Il reste donc dans common/ uniquement ce qui n'existe nulle part dans le repo : langue, ton, longueur des remarques, faux positifs à ne jamais produire — commun à tous les reviewers du projet.

Le déterministe avant le LLM

Un reviewer peut déclarer un precheck : un script dont la sortie est injectée comme faits établis.

« La clé checkout.title manque en de » est vérifiable — gratuit, instantané, sans faux positif. Le modèle garde le jugement : variables non substituées, pluriels, longueur, ton.

Ne jamais payer un LLM pour ce qu'un diff fait mieux.

Apprendre des retours, sans les absorber

Le bot ne mémorise rien d'une PR à l'autre : un point rejeté hier revient demain. Il n'apprend pas tout seul non plus — une règle absorbée en silence le rendrait progressivement aveugle sans que personne ne sache pourquoi.

Le mécanisme est l'attribution : une règle porte son auteur, sa PR et sa date, donc elle reste contestable.

reviewme feedback --pr 16974

- **PanierView.swift** — le reviewer `tech` disait : « Force-unwrap sur une URL de l'API… »
  **alice** a répondu (PR #42, 2026-01-15) : « L'API garantit ce champ par contrat. »

Ces lignes sont proposées, pas décidées. Un humain les relit — une réponse ponctuelle n'est pas une règle — puis les colle dans common/regles-terrain.md, qui est injecté à tous les reviewers du projet.

Consigne donnée au reviewerPourquoi
Applique ces règles, mais ce sont des avis, parfois contextuelsElles viennent d'une PR précise, pas de la doc du projet
Quand tu te tais à cause d'une règle, cite-laSans la mention, personne ne peut la contester — et un autre développeur peut être en désaccord
Si le code contredit franchement une règle, signale quand même et expliqueLa situation a pu changer, ou l'auteur parlait d'un autre cas

Le fichier étant versionné, une règle se discute en pull request et s'annule d'un git revert.

Pas de sous-agents

Un reviewer ne peut pas déléguer à des sous-agents, et l'outil Task n'est pas dans l'allowlist. Ce n'est pas un oubli.

Vérifié Un sous-agent n'hérite pas de l'allowlist de son parent : il utilise les outils de sa propre définition. Un parent restreint à Read,Glob,Grep a pu exécuter whoami via un sous-agent déclarant Bash. Comme la configuration d'un reviewer peut venir du dépôt reviewé — donc d'une Pull Request — ce serait rouvrir l'exécution de code arbitraire.

Pour faire varier le modèle selon la tâche, l'équivalent existe déjà et coûte moins cher : créer un reviewer de plus avec son propre model. C'est déclaratif, le nombre est borné, chaque exécution a son budget, et tout passe par l'allowlist du moteur.

Plugins

Un reviewer peut avoir besoin de skills ou d'agents qui ne vivent pas dans ReviewMe — outillage maison, analyse spécialisée. Il les déclare, le moteur les installe avant la review :

# reviewer.toml
[plugins]
marketplaces = ["owner/marketplace-repo"]   # ajoutés d'abord
install      = ["mon-plugin"]               # ou "mon-plugin@marketplace"

Idempotent : ce qui est installé ne l'est pas deux fois. Un échec n'affecte que le reviewer concerné.

Code tiers Installer un plugin fait tourner du code que vous n'avez pas écrit dans l'environnement de review, aux côtés des secrets du job. Un plugin se relit comme du code. Le moteur garde son allowlist d'outils : un skill de plugin n'obtient pas plus de droits que le reviewer qui l'invoque — ce qui limite aussi ce qu'un plugin très outillé peut faire ici.

Nommer un reviewer

L'id d'un reviewer est le nom de son dossier. Il est libre : tech, us et i18n sont les conventions du squelette, pas des valeurs imposées.

reviewers/securite-mobile/     # parfaitement valide
reviewers/perf/
reviewers/accessibilite/

Aucun code ne dépend de ces noms. Ce qui définit un reviewer, c'est son reviewer.toml et sa persona.

Une fois choisi, on n'y touche plus L'id entre dans le marqueur de déduplication. Le renommer sur un dépôt déjà commenté rend orphelins tous ses commentaires : ils seront reposés en double.

Contextes exigés

requires déclare les données externes sans lesquelles un reviewer n'a pas de sens. Absentes, il est skippé — jamais en erreur, les autres continuent.

ValeurCe qu'elle apporteFournie par
jira_ticketTitre, description et critères d'acceptation du ticket lié à la PRJIRA_BASE_URL, JIRA_EMAIL, JIRA_API_TOKEN

Seule valeur à ce jour. Une valeur inconnue est refusée au chargement : sans ce contrôle, requires = ["jira"] rendrait le reviewer inerte à vie, sans le moindre message.

Exemple complet : la config dans le dépôt reviewé

Quatre étapes, une seule fois. C'est la forme la plus simple pour démarrer sur un projet.

1 · Créer le squelette — init-project écrit directement au bon endroit :

cd mon-projet
REVIEWME_CONFIG_HOME=$PWD/.reviewme reviewme init-project mon-projet --reviewers tech

.reviewme/projects/mon-projet/
  common/style.md                        langue, ton, format des remarques
  reviewers/tech/reviewer.toml           mode de sortie, déclencheur, conventions à lire
  reviewers/tech/system.md               la persona

2 · Dire où sont les conventions — dans reviewers/tech/reviewer.toml :

output_mode = "inline"
priority    = 10

[context]
read = ["AGENTS.md", "CONTRIBUTING.md", "docs/"]   # lus à la source à chaque review

3 · Adapter la persona — reviewers/tech/system.md, en ajoutant ce qui est propre au projet :

## Contexte de ce projet
API Vapor (Swift), `StrictConcurrency` activé : signale tout état non-`Sendable`
capturé dans un contexte `async`. Requêtes N+1 et migrations non idempotentes
sont des `BLOCKER` ici.

4 · Brancher la CI — le dépôt est déjà cloné, il suffit de pointer dedans :

export REVIEWME_CONFIG_HOME="$CLONE_DU_PROJET/.reviewme"
export PROJECT=mon-projet
export GITHUB_TOKEN="$TOKEN_CI"
export REPO_PATH="$CLONE_DU_PROJET"

reviewme review --pr "$PR" --dry-run     # retirer --dry-run une fois calibré

Rien à cloner en plus, aucun credential supplémentaire. Recette complète pour Bitrise : deploy/bitrise-step.md ; pour GitHub Actions : deploy/github-actions/.

Le risque à couvrir Si la config vit dans le dépôt reviewé, une PR peut modifier sa propre review — adoucir une persona, désactiver un reviewer. Le moteur ferme les conséquences les plus graves : le .env d'une instance ne peut pas définir ce qui est exécuté ni où l'on s'authentifie (CLAUDE_BIN, tokens, PATH… sont ignorés), et un precheck ne peut pas sortir du dossier de son reviewer. Restent les changements de jugement : pour ceux-là, protéger .reviewme/ par CODEOWNERS, ou charger la config depuis la branche de base plutôt que depuis la PR.
En CI, plus sûr Matérialiser la config depuis la branche de base au lieu de l'arbre de la PR : 
CFG=$(mktemp -d)
git fetch --quiet --depth 1 origin develop
git archive FETCH_HEAD .reviewme | tar -x -C "$CFG" --strip-components=1
export REVIEWME_CONFIG_HOME="$CFG"
La PR ne peut alors plus influencer sa propre review, même avant merge.

En CI : l'instance épingle le moteur

En CI, pas de moteur qui change de version entre deux builds. L'instance le monte en submodule .core et épingle sa version : un seul clone ramène tout.

# dans le dépôt d'instance, une fois
git submodule add <url-du-moteur> .core

# en CI
git clone --recurse-submodules <url-de-l-instance> config
cd config && ./reviewme review --pr "$PR_NUMBER"

Le lanceur détecte .core seul, aucune variable à poser. Sans .venv, il passe par uv run.

Mettre à jour le moteur devient un geste daté : git -C .core pull puis commit du pointeur.

Le sens du montage C'est l'instance qui épingle le moteur, jamais l'inverse. Le moteur ne référence aucune instance, reste neutre, et peut être partagé ou publié — alors qu'un moteur qui monterait ses instances en submodules se salirait d'un commit de pointeur à chaque changement de persona.
Comprendre

Sous le capot

Du diff au commentaire inline, et les modules qui s'en chargent.

L'essentiel Le moteur renvoie des findings JSON ; ReviewMe valide chaque ligne contre le diff (sinon 422), déduplique par un fingerprint stable, poste en un seul write, et répond dans les threads quand une ligne a bougé.

1 · Findings structurés

claude -p, avec la persona du reviewer, répond par un JSON : summary + findings {path, line, severity, message, snippet, confidence}.

JSON invalide ? Repli en commentaire global plutôt qu'un crash. La review est livrée, en moins bien, jamais perdue.

2 · Validation anti-422

GitHub valide une review de façon atomique : un seul commentaire hors-diff rejette TOUTE la review.

diff_utils parse les patches et calcule les lignes commentables. Les findings hors-diff basculent dans le summary.

3 · Fingerprint & déduplication

Chaque commentaire porte un marqueur invisible : <!-- reviewme:REVIEWER:HASH -->, avec HASH = sha1(path + contenu de la ligne).

Indépendant du numéro de ligne et du texte narré par le LLM, donc stable entre deux runs.

On reconnaît nos commentaires par ce marqueur, jamais par l'auteur — sinon on toucherait les threads humains.

La clé de déduplication est le couple (reviewer, hash). C'est ce qui permet à deux reviewers de commenter la même ligne sans que l'un fasse disparaître l'autre.

Propriété clé Le hash porte le contenu de la ligne, pas son numéro : un commit qui décale le code ne recrée aucun commentaire. Le reviewer_id est un préfixe du marqueur et n'entre pas dans le hash. Verrouillé par tests/test_fingerprint_migration.py.
Piège REVIEWER_ID doit rester stable dans le temps pour un projet donné : le renommer rend orphelins tous les commentaires déjà postés, qui seront alors reposés en double. Même règle que pour le hash.

4 · Sur un nouveau commit

SituationCe que fait le bot
Le problème est là, la ligne n'a pas bougédédup rien de posté, rien de dit
Le problème est là, la ligne a bougéréponse dans le thread existant — jamais un nouveau commentaire
Le problème a disparu et la ligne a changéréponse « ce point n'apparaît plus — corrigé »
Le problème a disparu mais la ligne est identiquesilence on ne conclut rien

La dernière ligne est le garde-fou : un modèle qui varie d'un run à l'autre suffirait sinon à annoncer une correction imaginaire. On ne conclut qu'une chose vérifiable — GitHub a marqué le commentaire obsolète, donc la ligne a réellement changé.

Un reviewer ne répond que dans ses threads : le marqueur porte son identité.

4 · Ce que l'agent sait de la PR

À chaque review, l'agent reçoit ses remarques précédentes et les réponses humaines — pas seulement le diff.

SituationEffet
Un point déjà signaléIl ne le répète pas : il est déjà visible sur la PR
« C'est volontaire »Il n'y revient pas, même si la ligne a bougé
Un point corrigéSilence — pas de félicitations

Sans cet historique, un « c'est volontaire » est oublié dès que le code de la ligne change : le fingerprint diffère, et la remarque revient. C'est ce qui fait qu'une équipe finit par couper le bot.

Contenu tiers Les réponses viennent de développeurs : elles sont injectées comme données, avec la consigne explicite de n'y suivre aucune instruction.

4 · Cycle de vie des threads

SituationAction
Finding nouveauAjouté au batch inline
Finding déjà posté, toujours valideDédup — rien
Finding persiste, commentaire devenu outdated (nouveau commit)Réponse dans le thread existant (pas de doublon)
JSON moteur invalideFallback : commentaire global
422 résiduel sur le batchRepli : tout en commentaire global (rien perdu)

Le batch inline = un seul POST /pulls/{n}/reviews (respecte la limite de 80 créations/min).

Déployer

Quatre points d'entrée, trois cibles, et les garde-fous à connaître.

L'essentiel Tout passe par la même brique run_review() ; les points d'entrée ne font que résoudre une PR et l'appeler. Avant d'exposer quoi que ce soit, lire la section sécurité : l'auteur d'une PR n'est pas fiable.

Points d'entrée

Aucune logique de review dupliquée : chaque entrée résout une PR puis appelle run_review(). On choisit l'entrée selon le contexte de déploiement.

CLI (one-shot)

  • reviewme review --repo --pr
  • La brique commune
  • Idéal : CI, cron, test manuel

Webhook

  • Event pull_request → review
  • HMAC obligatoire (fail-closed)
  • Idéal : VPS temps réel

Poll

  • Boucle sur PR labellisées / toutes
  • Aucune exposition entrante
  • Mode legacy / dev

CI

  • GitHub Actions ou Bitrise
  • Appelle le CLI one-shot
  • 1 build = 1 review
Reco Démarrer par le CLI one-shot (rien à exposer, valide toute la chaîne). Passer au webhook pour le temps réel une fois le VPS exposé proprement (TLS + HMAC).

Déploiement

Quelle que soit la cible, le déploiement clone l'instance (avec le moteur en submodule .core) et appelle son lanceur — cf. Démarrer § En CI.

Runner Linux, même pour un projet iOS La review ne compile rien : elle lit un diff et des fichiers texte, sans Xcode ni toolchain. Bitrise permet de surcharger le stack par workflow (meta.bitrise.io.stack), donc une app iOS peut avoir son workflow de review sur Linux — bien moins cher à la minute qu'un runner macOS. Exemple complet : deploy/bitrise-step.md.

Recettes prêtes dans deploy/. Le point à trancher au déploiement reste l'auth du moteur en session non interactive : ANTHROPIC_API_KEY, ou une passerelle d'entreprise via ANTHROPIC_BASE_URL.

Historique sur un runner éphémère

Un runner de CI repart de zéro à chaque build : pas de statistiques cumulées, et une relance sur le même commit repaie une review qui ne postera rien.

Le moteur écrit deux choses dans data/ :

data/reviews/Le détail d'une review, résumé du modèle inclusNon contenu de PR réelles
# Bitrise : deux steps autour de la review
- restore-cache@2:
    inputs: [key: reviewme-ios-history]

Les statistiques sont idempotentes par (PR, commit) : rejouer un build ne gonfle pas les totaux. Le dashboard les sert sur /api/stats, y compris quand le détail des reviews est absent.

Le cache n'est pas un stockage Il s'évince et il est scopé par clé. Pour des compteurs, une perte coûte un trou dans l'historique. Pour autre chose, prévoir un vrai store.

Ce n'est pas qu'un endpoint claude -p est un agent : il ouvre les fichiers du dépôt, cherche dedans, lit l'historique git. Une API de complétion classique ne fait rien de tout ça. Y basculer, c'est un backend à écrire, pas une variable à poser.

Sécurité

À lire avant tout déploiement Un auteur de PR est non fiable. Sans précautions, le diff peut pousser le moteur à écrire des fichiers (RCE) ou exfiltrer des secrets dans un commentaire public. Les garde-fous ci-dessous sont implémentés ; le sandbox réseau reste à câbler au déploiement.

Garde-fous en place

MenaceMitigation (implémentée)
Écriture arbitraire (injection → RCE)Allowlist verrouillée Read,Glob,Grep,Bash(git log/show/diff) — pas de Write, jamais --dangerously-skip-permissions
Exfiltration de secretsDiff traité comme donnée non fiable ; scrub (tokens, clés, chemins absolus) sur tout texte avant post
Webhook usurpéHMAC X-Hub-Signature-256 en temps constant, corps brut, fail-closed sans secret
Token trop puissantPAT fine-grained, 1 repo, PR R/W (pas de classic repo)
Dashboard exposéCORS * retiré, endpoint d'écriture /api/requeue supprimé, read-only 127.0.0.1
Fuite de secrets/données.gitignore couvre .env et data/
Reste à faire au déploiement La mitigation n°1 de la prompt-injection — exécuter claude -p dans un sandbox sans réseau sortant (hors GitHub) et avec un Read confiné au clone cible — n'est pas gérable dans le code : à câbler au niveau infra (conteneur/systemd + firewall). Le scrub est la dernière barrière, pas la seule.
Identité dédiée Faire tourner le bot sous une GitHub App plutôt qu'un PAT humain : token court renouvelé automatiquement, permissions explicites, et les commentaires arrivent sous <slug>[bot] au lieu du compte d'une personne. Il suffit de renseigner GITHUB_APP_ID et GITHUB_APP_PRIVATE_KEY_PATH.

Statut & limites

Ce qui tourne, ce qui n'existe pas encore, et ce qu'il faut calibrer.

L'essentiel Le cœur est validé sur de vraies PR : commentaires inline ancrés aux bonnes lignes, aucun doublon après un commit qui décale le code, et plusieurs reviewers en parallèle sur un même diff. Restent deux réglages à faire à la main sur chaque dépôt : le seuil de confiance et le plafond de coût.

Validé sur de vraies PR

VérificationRésultat
Inline sur les bonnes lignesOK re-ancrage par le contenu quand le modèle se trompe de quelques lignes
Dédup sur re-reviewOK même commit et commit suivant : zéro doublon
Fan-out multi-reviewersOK deux reviewers en parallèle, une seule écriture GitHub
Déclenchement par le diffOK un reviewer ne tourne que si la PR le concerne
Conventions lues dans le dépôtOK et un chemin obsolète est signalé

À calibrer sur chaque dépôt

RéglagePourquoi
CONFIDENCE_THRESHOLDÀ 80, l'essentiel des findings est filtré sur du code déjà relu. Passer quelques PR en --dry-run et regarder ce qui aurait été posté avant de trancher.
MAX_BUDGET_USDLe coût suit la taille du diff : un gros diff coûte plus cher qu'un reviewer de plus. Le plafond s'applique par reviewer.
MAX_COMMENTS_PER_PRLe facteur d'abandon d'un bot de review est le bruit, pas le manque de findings.

Ce qui n'existe pas

AbsentConséquence pratique
Sandbox de déploiementÀ câbler à l'infra (pas de réseau sortant, FS confiné). C'est la mitigation de fond contre la prompt injection — cf. Sécurité.
REQUEST_CHANGES bloquantLe bot ne pose que des COMMENT. Exige une GitHub App comme identité.
Resolve / unresolve des threadsGitHub replie déjà les commentaires devenus obsolètes.
Commentaires multi-lignes et suggestionsUn finding s'ancre sur une seule ligne, côté droit du diff.
Arrêt net au plafond de coût d'une PRLes reviewers tournent en parallèle : le dépassement est journalisé, pas interrompu.
